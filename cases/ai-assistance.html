Designing AI Assistance Проектирование AI-ассистента

Security investigation often starts with messy technical data: raw events, long SQL queries, regex patterns, and alerts that need to be interpreted quickly. I designed KIRA-powered AI workflows for Kaspersky OSMP to help SOC analysts generate hunting queries, create normalization patterns, explain event fields, and summarize alerts directly inside their existing tools. The goal was to make AI feel like a practical assistant, not a separate chatbot or a black-box autopilot.

Расследование инцидентов часто начинается с «грязных» данных: сырые события, длинные SQL-запросы, регулярные выражения и алерты, которые нужно быстро интерпретировать. Я спроектировала AI-воркфлоу на KIRA для Kaspersky OSMP — помогают SOC-аналитикам генерировать hunting-запросы, создавать паттерны нормализации, объяснять поля событий и суммаризовать алерты прямо внутри их инструментов. Цель — сделать AI практическим ассистентом, а не отдельным чатботом или чёрным ящиком-автопилотом.

01. Generating SQL queries for threat hunting 01. Генерация SQL-запросов для threat hunting

Problem

Threat hunting often starts with SQL, but writing a good query takes time: analysts need to know the event schema, choose the right fields, write conditions correctly, and adjust the time range. In some customer environments, hunting queries can grow to 10+ lines, turning even a simple investigation intent into a manual, syntax-heavy task.

Solution

Instead of building a long SQL query from scratch, analysts can describe what they need in one sentence, such as "show all EDR file creation events from the last 24 hours." KIRA turns that intent into a structured SQL query and suggests the relevant time period, so the analyst can start from a working draft instead of a blank editor.

Design decision

I designed KIRA as a drafting assistant, not an autopilot: it generates SQL inside the existing hunting workspace, but the analyst reviews, edits, and applies the query before running it. This helps analysts move faster from intent to a runnable query without losing control.

Проблема

Threat hunting часто начинается с SQL, но написать хороший запрос — время: нужно знать схему событий, выбрать поля, правильно написать условия, скорректировать интервал. У некоторых клиентов hunting-запросы разрастаются до 10+ строк, превращая простое намерение в ручной синтаксический труд.

Решение

Вместо длинного SQL с нуля аналитик описывает задачу одним предложением, например: «покажи все EDR-события создания файлов за последние 24 часа». KIRA превращает намерение в структурированный SQL и подсказывает нужный период — аналитик стартует с рабочего черновика, а не с пустого редактора.

Дизайн-решение

Спроектировала KIRA как ассистента-черновика, а не автопилот: SQL генерируется прямо в хантинг-воркспейсе, но аналитик проверяет, правит и применяет запрос перед запуском. Помогает быстрее двигаться от идеи к запросу, не теряя контроль.

02. Explaining unclear event fields 02. Объяснение непонятных полей событий

Problem

Security events often contain raw, technical, or poorly readable field values: messages, command-line fragments, encoded strings, vendor-specific data, or long unstructured text. To understand whether a value matters for the investigation, analysts had to inspect it manually and search for additional context.

Solution

I designed a KIRA-powered flow that lets analysts send a selected event field to AI directly from the event context. KIRA analyzes the value and returns a readable explanation with supporting details and a risk-oriented assessment.

Design decision

I treated the AI response as supporting context, not a final verdict. The explanation helps analysts understand unfamiliar event data faster, while the decision to investigate further stays with the analyst.

Проблема

События безопасности часто содержат сырые, технические или плохо читаемые значения: сообщения, фрагменты командной строки, закодированные строки, вендор-специфичные данные, длинный неструктурированный текст. Чтобы понять, важно ли значение для расследования, аналитик разбирал его вручную и искал дополнительный контекст.

Решение

Спроектировала KIRA-поток, где аналитик отправляет выбранное поле события в AI прямо из контекста события. KIRA анализирует значение и возвращает читаемое объяснение с деталями и риск-ориентированной оценкой.

Дизайн-решение

Ответ AI — это поддерживающий контекст, а не финальный вердикт. Объяснение помогает быстрее понять незнакомые данные, но решение о дальнейшем расследовании остаётся за аналитиком.

My initiative: keeping reports where the investigation happens

The original requirement saved KIRA reports as tasks in Task Manager, a shared list that also contains imports, exports, and other background jobs. I saw a discoverability problem: after a few days, analysts would have to remember when a request was made and search through similar tasks to find a specific report.

I proposed adding a dedicated tab inside the event card, where all KIRA reports for that event are collected. Analysts can instantly see which fields were already analyzed, reopen previous reports, and continue investigation without leaving the event context.

image placeholder

Моя инициатива: держать отчёты там, где идёт расследование

Изначально отчёты KIRA сохранялись как задачи в Task Manager — общем списке рядом с импортами, экспортами и другими фоновыми джобами. Я увидела проблему discoverability: через несколько дней аналитик должен помнить, когда был запрос, и искать нужный отчёт среди похожих задач.

Я предложила добавить отдельный таб внутри карточки события — там собираются все отчёты KIRA по конкретному событию. Аналитик сразу видит, какие поля уже проанализированы, может открыть прошлые отчёты и продолжить расследование, не покидая контекст события.

03. Generating regex patterns for event normalization 03. Генерация regex-паттернов для нормализации событий

Problem

To make raw events usable in KUMA, analysts and content engineers need to normalize them into structured event fields. For regexp-based parsing, this means manually writing RE2 regular expressions with named capture groups, checking that the expression matches the event, and mapping extracted values to KUMA fields. This is precise, syntax-heavy work that takes time and is easy to get wrong.

Solution

I designed a KIRA-powered flow inside the normalizer editor that generates one or several regular expressions from an event example. Instead of starting from a blank input, the user can provide a raw event and get suggested parsing patterns with named groups. KIRA also highlights matched groups in the event, making it easier to understand what each part of the expression extracts.

Design decision

I made the generated regex transparent and reviewable, not just automatically inserted. Group highlighting connects the raw event to the generated expression, helping users validate the result before applying it to the normalization scheme. This turns regex creation from manual syntax writing into guided review and adjustment.

Проблема

Чтобы сырые события были полезны в KUMA, аналитики и content-инженеры нормализуют их в структурированные поля. Для regex-парсинга это значит вручную писать RE2-выражения с именованными группами, проверять совпадение и маппить значения в поля KUMA. Точная синтаксическая работа, где легко ошибиться.

Решение

Спроектировала KIRA-поток внутри редактора нормализатора: генерирует одно или несколько regex из примера события. Пользователь даёт сырой ивент и получает подсказанные паттерны с именованными группами. KIRA подсвечивает совпавшие группы в событии — легче понять, что извлекает каждая часть выражения.

Дизайн-решение

Сделала генерируемый regex прозрачным и проверяемым, а не автоматически вставляемым. Подсветка групп связывает сырой ивент с выражением — пользователь валидирует результат перед применением. Regex-создание превращается из синтаксической писанины в направляемый ревью и настройку.
